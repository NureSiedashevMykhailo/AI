## ВИХІД 3: Класифікація питань (Q-ID)

### Блокуючі питання (Блокують генерацію макетів та перевірку коду)

Наразі критичних нерозв'язаних блокерів немає. Після застосування виправлення DEF-01 (переведення прав на статус суворо до Assignee Only згідно з контрольною матрицею) та DEF-02 (заборона переходу в In Progress без попередньо призначеного Assignee) усі правила поведінки інтерфейсу стають детермінованими.
### Питання, які можна безпечно відкласти на етап імплементації (Non-blocking)

- **Q-10 (Візуальний формат бейджів пріоритету):** Конкретна колірна схема (HEX-коди кольорів) для Critical, High, Normal, Low, Not Set у дизайн-системі. Не впливає на логіку контрактів та структуру екранів.- **Q-11 (Пагінація vs Нескінченний скрол):** Для MVP команди з трьох осіб кількість заявок невелика (A-02, A-03). Питання механіки підвантаження записів (чи потрібна пагінація при >50 заявок) не блокує побудову базових фреймів.   

## ВИХІД 4: Вердикт щодо готовності плану

### PLAN READY (з урахуванням виправлень DEF-01 та DEF-02)

**Пояснення:**
 План мінімальної системи екранів повністю покриває всі User Stories та критерії приймання першого релізу (Release MVP: US-01..US-08).   Збережено всі негативні умови: заборона видалення (BR-10), заборона аудиту/історії (BR-11), блокування невалідних переходів (BR-08.1), обробка збою збереження коментаря (AC-06.5).   Відсутні зайві продуктові сутності: немає окремих екранів для пріоритетів, статусів чи коментарів; відсутні екрани для неінтерфейсних NFR (HTTPS, Backup); US-09 (файли) та SR-10/SR-11 (AI) надійно виключені.   Після синхронізації дозволів на зміну статусу з контрольною матрицею (виключно Assignee), конфлікти між вимогами та архітектурними переходами повністю ліквідовані.
**Застереження:**
 Оцінка PLAN READY є рекомендацією архітектора вимог; остаточне рішення щодо початку фази верстки приймає провідний розробник та Product Owner.
### Перелік точково змінених пунктів у контрактах та переходах

#### Контракт екрана S-03 (Issue Details) — Елементи C-03.2 та C-03.3
Старе формулювання: Доступно для Any Actor (TL/TM) згідно з AD-01.Нове виправлене формулювання (DEF-01): Enabled: Лише якщо поточний автентифікований користувач є призначеним Assignee даного issue. Для будь-якого іншого користувача (включно з Team Lead, якщо він не призначив самого себе виконавцем) селектор та кнопка Apply Status заблоковані або приховані. Відображається лише статичний бейдж поточного статусу.
#### Таблиця переходів (Transition Table) — Записи T-14, T-15, T-16, T-17
Стовпець Actor змінено з Any Actor (TL/TM) на Assignee only.До стовпця Preconditions для T-14 додано: Assignee != Not Set (виконавець обов'язково призначений).
#### Таблиця переходів — Додано новий контрольний запис T-14a (Заборонена дія)
From: S-03 | Actor: Team Member (Non-assignee) або Team Lead (Non-assignee) | Trigger: Спроба кліку/зміни селектора статусу | Preconditions: Користувач не є Assignee | To: S-03 (Немає переходу) | Visible result: Контрол заблокований, дія не виконується, перехід відсутній | Source: [S1: AC-07.4, Контрольна матриця].
#### Тест-кейс TC-13
Передумову оновлено: користувач автентифікований як призначений виконавець (Assignee) цієї заявки.
#### Тест-кейс TC-08 (Розділено на TC-08a та TC-08b)
Тест-кейс структуровано на два взаємодоповнюючі записи з фіксованими контекстами:
- **TC-08a (Заборона зміни Assignee та Priority для Team Member):** перевіряє відсутність кнопок Apply Assignee / Apply Priority та відображення полів у вигляді статичного тексту.
- **TC-08b (Заборона зміни статусу для Non-assignee):** перевіряє блокування селектора C-03.2 та кнопки Apply Status для користувача, який не є поточним Assignee (перехід T-14a блокує дію згідно з AC-07.4, DEF-01).
