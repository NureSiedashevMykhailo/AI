# Архітектура інтерфейсу та мінімальна система екранів: Mini Issue Tracker (Release MVP)

## 1. Специфікація поверхонь та станів (Surfaces & States)

Класифікація сутностей:
- **Product Screen (Екран):**  Самостійна сторінка вебзастосунку з власним маршрутом URL (S-01, S-02, S-03).
- **Screen State (Стан екрана):**  Режим відображення того самого базового екрана без зміни структури сторінки (S-02-A, S-02-B, S-02-C).
- **Modal / Overlay (Модальне вікно):**  Фокусний шар поверх базового екрана, який блокує взаємодію з підкладкою (M-01).
- **Component State (Стан компонента):**  Локальна зміна всередині блоку (наприклад, стан помилки інпуту чи індикатор завантаження).
- **Figma Frame (Фрейм):**  Статичний або інтерактивний артборд у Figma, необхідний для візуальної фіксації певного стану чи кроку користувача.

## Розрахунок кількості продуктових сутностей та Figma Frames

Кількість продуктових екранів (Routes/Screens): 3 (S-01 Authentication Boundary, S-02 Issues List, S-03 Issue Details).
Кількість модальних вікон (Modals): 1 (M-01 Create Issue Modal).
Кількість продуктових станів (States): 3 стани списку (S-02-A, S-02-B, S-02-C).
Необхідна кількість Figma Frames для повної демонстрації сценаріїв MVP: 9 фреймів.

- **Frame 01** [S-01]: Стартова заглушка вибору ролі/акаунта (TL / TM1 / TM2).
- **Frame 02** [S-02-C]: Список задач — стан повної відсутності даних (Empty State).
- **Frame 03** [S-02-A]: Основний список усіх задач (All Issues) з активними записами.
- **Frame 04** [S-02-B]: Список задач з увімкненим фільтром «Important Issues» (High/Critical та не Closed).
- **Frame 05** [M-01 Default]: Модальне вікно створення заявки (чисті обов'язкові інпути).
- **Frame 06** [M-01 Validation Error]: Модальне вікно з помилкою «Title is required» та перевищенням ліміту 50 символів.
- **Frame 07** [S-03 Team Lead View]: Деталі задачі очима Team Lead (активні селектори Assignee та Priority з кнопками Apply; селектор Status відображається як заблокований / статичний бейдж, оскільки для задачі #101 призначеним Assignee є Team Member 1 згідно з AC-07.4, DEF-01, D-10).
- **Frame 08** [S-03 Team Member View]: Деталі задачі очима Team Member 1 (селектор Status активний з кнопкою Apply Status, оскільки користувач є призначеним Assignee задачі #101; поля Assignee та Priority відображаються як суто Read-Only текст без кнопок дій згідно з US-03, US-04, D-05).
- **Frame 09** [S-03 Comment Error State]: Деталі задачі з відображенням помилки невдалого збереження коментаря (Failed save).

## 3. Текстові User Flows за сценаріями

### Сценарій 1: Створення та перегляд issue

1. Користувач перебуває на `S-01`, обирає свій профіль (наприклад, Team Member 1) та потрапляє на `S-02-A` (або `S-02-C`, якщо база порожня).
2. На екрані `S-02-A` користувач натискає кнопку `+ Create Issue`.
3. Система відкриває модальне вікно `M-01`.
4. Користувач вводить у поле Title назву дефекту (наприклад, «Button does not respond», валідація <=50 символів) та заповнює поле Description.
5. Користувач натискає кнопку `Create`.
6. Система виконує валідацію: атрибути валідні. Модальне вікно `M-01` закривається.
7. Відкривається оновлений екран `S-02-A`, де у верхньому рядку (за правилом Triage Inbox / Created_at DESC) з'являється нова заявка з системними атрибутами: ID (#108), заданий Title, Status = Open, Priority = Not Set, Assignee = — (Unassigned).
8. Користувач клікає на цей новий рядок у таблиці.
9. Відбувається перехід на екран `S-03`, де повністю відображені всі збережені дані: Title, Description, Author (Team Member 1), дата створення, статус Open, бейдж пріоритету Not Set та порожній блок коментарів.

### Сценарій 2: Призначення виконавця та встановлення Priority (роль Team Lead)

1. Користувач автентифікується через `S-01` під роллю Team Lead та переходить до `S-02-A`.
2. У списку задач Team Lead обирає щойно створену задачу без пріоритету та переходить на `S-03`.
3. На екрані `S-03` Team Lead бачить активний блок керування заявкою:
   - Селектор Assignee активний. Team Lead обирає значення «Team Member 1» і натискає кнопку `Apply Assignee` біля селектора. Значення фіксується (T-10).
   - Селектор Priority активний. Team Lead обирає значення Critical і натискає кнопку `Apply Priority` біля селектора. Значення фіксується (T-13).
4. Team Lead натискає кнопку `← Back to List` і повертається на `S-02-A`. У таблиці списку заявка тепер відображає: Priority: Critical, Assignee: Team Member 1.

### Сценарій 3: Дозволені статусні переходи (повний життєвий цикл)

1. Призначений виконавець заявки (Assignee, згідно з вимогою AC-07.4 та рішенням DEF-01, D-10; для будь-якого іншого користувача селектор заблокований) відкриває заявку на екрані `S-03`, поточний стан якої Status: Open.
2. Виконавець відкриває селектор статусу: доступна лише опція In Progress. Користувач обирає In Progress і тисне `Apply Status` (T-14). Статус заявки змінюється на In Progress.
3. Після завершення робіт виконавець знову звертається до селектора статусу на `S-03`: доступна лише опція Resolved. Користувач обирає її та тисне `Apply Status` (T-15). Статус стає Resolved.
4. Для остаточного закриття задачі користувач у селекторі статусу бачить дві опції: Closed та In Progress. Користувач обирає Closed і тисне `Apply Status` (T-16). Заявка переходить у фінальний стан Closed. Подальші вихідні зміни статусу стають недоступними.

### Сценарій 4: Повернення Resolved у роботу (Reopen)

1. Заявка знаходиться на екрані `S-03` у стані Status: Resolved. Згідно з бізнес-правилом BR-09.1 вона вважається вирішеною, але не закритою.
2. Під час перевірки виявлено, що дефект усунуто не повністю.
3. Призначений виконавець відкриває селектор статусу, де доступна опція In Progress (відповідно до дозволеного переходу Resolved → In Progress за BR-08.1).
4. Користувач обирає In Progress і натискає `Apply Status` (T-17).
5. Заявка повертається в активну розробку (Status: In Progress).

### Сценарій 5: Додавання коментаря (Success та Error)

1. Користувач на екрані `S-03` переходить до блоку коментарів унизу сторінки.
2. **Кейс Success:** Користувач вводить текст «Fixed in staging build» у поле коментаря та тисне `Send Comment`. Система зберігає запис. У стрічці коментарів з'являється новий блок: Ім'я автора, позначка поточної дати/часу та текст коментаря (T-19). Поле введення очищується.
3. **Кейс Error (Failed save):** Користувач вводить коментар і тисне `Send Comment`, але сервер повертає помилку мережі або збереження. Система НЕ додає запис у стрічку, введений текст зберігається в полі вводу, а над полем відображається повідомлення про помилку: «Failed to save comment. Please try again.» (T-20).

### Сценарій 6: Перегляд важливих задач (Important Issues)

1. Користувач перебуває на екрані `S-02-A`, де відображаються всі задачі з різними пріоритетами (Low, Normal, High, Critical, Not Set) та статусами (Open, In Progress, Resolved, Closed).
2. Користувач клікає на таб/перемикач фільтра `Important Issues`.
3. Система без переходу на окрему сторінку перемикає екран у стан `S-02-B` (T-08).
4. У таблиці залишаються виключно заявки, які відповідають предикату:
   - Priority = High або Critical;
   - Status != Closed (заявка #104 зі статусом Resolved з пріоритетом Critical обов'язково відображається, оскільки Resolved не дорівнює Closed).
5. Усі задачі з пріоритетами Low, Normal, Not Set або зі статусом Closed (#107) повністю приховані.
6. Користувач клікає таб `All Issues` і повертається до повного списку `S-02-A` (T-09).

### Сценарій 7: Спроба виконання забороненої дії неуповноваженим користувачем

1. Користувач входить під роллю Team Member (TM1) на `S-01` та відкриває задачу на екрані `S-03`.
2. Користувач намагається змінити пріоритет або перепризначити виконавця.
3. **Результат в UI:** Поля Assignee та Priority для Team Member відображаються у вигляді звичайного статичного тексту (або заблокованих полів без списків, що випадають). Кнопки Apply біля цих полів повністю відсутні.
4. Будь-який клік по цих зонах не викликає реакції, перехід не відбувається (T-12, D-05). Інтерфейс виключає можливість відправки невалідного запиту неуповноваженою роллю.

### Сценарій 8: Порожній стан списку (Empty State)

1. База даних системи чиста (заявки ще не створювалися) або всі дані видалено на бекенді.
2. Користувач входить у систему через `S-01`.
3. Система завантажує екран списку у стані `S-02-C`.
4. Замість таблиці користувач бачить графічну плашку та повідомлення: «No issues found. Create the first issue to get started.» Також на екрані присутня активна кнопка `+ Create Issue`.
5. Клік на кнопку відкриває модалку `M-01`, і після збереження першої задачі екран автоматично переходить у повноцінний стан `S-02-A`.

## 4. Чого НЕ слід додавати до інтерфейсу (Антипатерни для MVP)

Навіть якщо зазначені елементи є типовими для трекерів на кшталт Jira або Linear, їхнє додавання до даного релізу суворо заборонене:

### Кнопка або пункт меню «Видалити заявку» (Delete Issue):
- **Чому заборонено:** Пряма заборона бізнес-правилом BR-10 («Issues не видаляються із системи») та первинним опитуванням стейкхолдерів. Усі заявки зберігаються постійно.

### Вкладка або блок «Історія змін / Журнал активності» (Activity Log / Audit Trail):
- **Чому заборонено:** Бізнес-правило BR-11 однозначно визначає: «У першій версії системи окрема користувацька історія змін issue не передбачається». На екрані S-03 має бути присутній лише блок створення та перегляду коментарів (US-06), без системних записів про те, хто і коли змінив статус чи пріоритет.

### Зона завантаження файлів / Drag-and-drop attachment:
- **Чому заборонено:** Функціонал вкладень (US-09) офіційно перенесено в категорію Deferred (поза Release MVP) через технічні ризики (необхідність антивірусного сканування, керування сховищем та окремих бекапів). Жодні скріпки, зони перетягування файлів чи кнопки «Attach file» не повинні проєктуватися ні в формі M-01, ні на сторінці S-03.
