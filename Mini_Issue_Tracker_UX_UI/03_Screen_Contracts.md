# Developer-Verifiable Screen Contracts: Mini Issue Tracker (Release MVP) — v1.0 APPROVED

## 1. Специфікація контрактів екранів та станів (Screen Contracts)

### S-01: Authentication Boundary (Placeholder)

#### 1. ID, призначення, actors, entry conditions

- **ID:** S-01
- **Призначення:** Демонстраційна межа автентифікації (Simulation Boundary) для навчального тестування та перегляду макета/прототипу під одним із 3 фіксованих облікових записів (без реєстрації, паролів чи сторонніх SSO-провайдерів). [APPROVED: D-02]
- **Actors:** Team Member (TM1, TM2), Team Lead (TL).
- **Entry conditions:** Запуск вебзастосунку; демонстраційний старт сесії під обраним профілем.

#### 2. Visible data

- **User List / Profiles:** Обов’язкове. Відображає рівно 3 доступні облікові записи (Team Lead, Team Member 1, Team Member 2). Відсутнє значення не допускається (системна константа).
- **Selected User Indicator:** Необов’язкове до моменту вибору. Якщо не вибрано — відображається плейсхолдер "Select user". [APPROVED: D-02]

#### 3. Controls

- **C-01.1 |** User Selector | Radio group / Dropdown | Visible: Always; Enabled: Always | Trigger: Клік по елементу списку | Результат: Фіксація обраного акаунта як активного для входу в демонстраційний прототип. [APPROVED: D-02]
- **C-01.2 |** Login Button | Primary Action Button | Visible: Always; Enabled: Коли обрано користувача в C-01.1 (Disabled, якщо значення не обрано) | Trigger: Click | Результат: Ініціалізація сесії обраного користувача, виклик переходу T-01. [APPROVED: D-02]

#### 4. States

- **Default state:** Радіо-група/дропдаун без попереднього вибору або перший у списку; кнопка Login заблокована (якщо вибір не зроблено).
- **Empty state:** Не застосовується (пул користувачів фіксований у коді/БД).
- **Validation state:** Не застосовується.
- **Error state:** Неможливість ініціалізації сесії (Network Error) → відображається alert: "Authentication service unavailable".

#### 5. Transitions

- **Incoming:** Запуск застосунку / прямий URL.
- **Outgoing:** T-01 → S-02-A (за наявності issues) або S-02-C (якщо база issues порожня).

#### 6. Рівні верифікації

- **У макеті (Figma):** Наявність статичного фрейму з трьома акаунтами та кнопкою Login.
- **У прототипі (Clickable):** Клік на профіль активує стан кнопки Login, перехід веде на екран списку.
- **Лише в реалізації:** Запис контексту сесії (ідентифікатор користувача, роль) у сховище/state застосунку, захист приватних роутів від неавторизованого доступу.

### S-02: Issues List Screen (Стани S-02-A, S-02-B, S-02-C)

#### 1. ID, призначення, actors, entry conditions

- **ID:** S-02 (Базовий контейнер із трьома станами: S-02-A All, S-02-B Important, S-02-C Empty).
- **Призначення:** Централізований перегляд зареєстрованих проблем команди з можливістю швидкого фільтрування важливих невирішених задач та ініціації створення нової заявки.
- **Actors:** Team Member, Team Lead.
- **Entry conditions:** Користувач автентифікований у S-01.

#### 2. Visible data (для кожного рядка в таблиці списку)

- **Issue ID:** Обов’язкове. Системний числовий/рядковий ідентифікатор. Відсутнє значення неможливе.
- **Title:** Обов’язкове. Текстовий рядок (до 50 символів). Відсутнє значення неможливе.
- **Status:** Обов’язкове. Одне зі значень: Open, In Progress, Resolved, Closed.
- **Priority:** Обов’язкове поле відображення. Значення: одне з Low, Normal, High, Critical. Вигляд відсутнього значення: нейтральний контурний сірий бейдж "Not Set" (#D1D5DB без заливки). [APPROVED: D-03]
- **Assignee:** Необов’язкове. Ім’я/ідентифікатор призначеного члена команди. Вигляд відсутнього значення: "—" (Unassigned).
- **Active User Info (в Header):** Ім'я поточного автентифікованого користувача та його роль ("User: Alex (Team Lead)").

#### 3. Controls

- **C-02.1 |** Filter Segment: All Issues | Tab / Segmented Button | Visible: Always (крім S-02-C); Enabled: Always | Trigger: Click | Результат: Перемикання списку в стан S-02-A (показ усіх записів), перехід T-09. [APPROVED: D-01]
- **C-02.2 |** Filter Segment: Important Issues | Tab / Segmented Button | Visible: Always (крім S-02-C); Enabled: Always | Trigger: Click | Результат: Перемикання списку в стан S-02-B (застосування предиката Important), виклик переходу T-08. [APPROVED: D-01]
- **C-02.3 |** Create Issue Button | Primary Action Button | Visible: Always; Enabled: Always | Trigger: Click | Результат: Відкриття модального вікна M-01 поверх поточного екрана (перехід T-02).
- **C-02.4 |** Issue Row | Table Row / Clickable Item | Visible: За наявності issues; Enabled: Always | Trigger: Click по рядку | Результат: Відкриття сторінки деталей обраної заявки S-03 (перехід T-06).

#### 4. States

- **S-02-A (Default state):** Активний таб All Issues. Відображаються всі записи з БД незалежно від статусу чи пріоритету.
  - *Комбіноване бізнес-правило сортування (Triage Inbox Model):* За замовчуванням список сортується за `Created_at DESC`. Це гарантує, що нові необроблені та щойно створені заявки (включно з #108 із Priority: Not Set) закріплюються у верхній вхідній зоні (Triage Inbox) до моменту розгляду та встановлення пріоритету лідом (покриває TC-01). При кліку на заголовок Priority застосовується сортування за рівнем важливості: Critical → High → Normal → Low → Not Set (непріоритезовані заявки розташовуються в кінці списку, покриває специфікацію брифу). [APPROVED: D-12]
- **Empty Filter Sub-state:** Якщо жодна заявка не підпадає під умову фільтра Important, таблиця приховується і виводиться текст: "No important open issues found".
- **S-02-C (Empty state):** Повна відсутність зареєстрованих issues у системі. Таблиця та фільтри приховані; по центру екрана виводиться текст: "No issues found. Create the first issue to get started." та активна кнопка Create Issue (C-02.3).
- **Validation / Error states:** Збій завантаження списку даних (Network 500) → текст помилки: "Failed to load issues. Please refresh the page.".

#### 5. Transitions

- **Incoming:** T-01 (із S-01), T-03 / T-05 (повернення з M-01), T-07 (повернення з S-03).
- **Outgoing:** T-02 (до M-01), T-06 (до S-03), T-08 (внутрішній стан S-02-A → S-02-B), T-09 (внутрішній стан S-02-B → S-02-A).

#### 6. Рівні верифікації

- **У макеті (Figma):** Наявність рівно 5 колонок таблиці (ID, Title, Status, Priority, Assignee), візуальний вигляд "Not Set" (#D1D5DB) та "—" (Unassigned), підсвічування активного фільтра, вигляд Empty State.
- **У прототипі (Clickable):** Клік на фільтри змінює склад рядків; клік на рядок веде до S-03; клік на Create Issue відкриває M-01.
- **Лише в реалізації:** Точна серверна або клієнтська фільтрація записів за предикатом Important, пагінація/скролінг при великій кількості рядків.

### M-01: Create Issue Modal

#### 1. ID, призначення, actors, entry conditions

- **ID:** M-01
- **Призначення:** Модальне вікно введення обов'язкових первинних даних для реєстрації нової проблеми в системі.
- **Actors:** Team Member, Team Lead.
- **Entry conditions:** Клік по кнопці C-02.3 на екрані S-02.

#### 2. Visible data

- **Користувацькі поля (вводяться вручну):**
  - **Title:** Обов’язкове. Текстовий інпут, ліміт — максимум 50 символів. Вигляд відсутнього значення: плейсхолдер "Enter issue title (max 50 chars)". Індикатор ліміту: "50/50". [APPROVED: D-09]
  - **Description:** Обов’язкове. Багаторядковий інпут (textarea). Вигляд відсутнього значення: плейсхолдер "Enter issue description".
- **Системно генеровані атрибути (НЕ відображаються у формі введення, генеруються автоматично):**
  - **ID:** унікальний ідентифікатор (#108).
  - **Status:** встановлюється суворо в Open.
  - **Priority:** встановлюється суворо у відсутнє значення Not Set.
  - **Author:** ідентифікатор поточного автентифікованого користувача.
  - **Created_at:** поточний серверний timestamp.

#### 3. Controls

- **C-01M.1 |** Title Input | Text Input | Visible: Always; Enabled: Always | Trigger: Введення тексту | Результат: Зміна значення Title; блокування вводу понад 50 символів (або лічильник). [APPROVED: D-09]
- **C-01M.2 |** Description Input | Textarea | Visible: Always; Enabled: Always | Trigger: Введення тексту | Результат: Зміна значення Description.
- **C-01M.3 |** Create Button | Primary Action Button | Visible: Always; Enabled: Always | Trigger: Click | Результат: Валідація форми. Якщо успішно — запис у БД, закриття модалки, виклик переходу T-05.
- **C-01M.4 |** Cancel / Close Button | Secondary Action Button / Icon | Visible: Always; Enabled: Always | Trigger: Click | Результат: Закриття модального вікна без збереження даних, виклик переходу T-03. [APPROVED: D-01]

#### 4. States

- **Default state:** Обидва поля вводу чисті; фокус на полі Title.
- **Empty state:** Не застосовується.
- **Validation state:**
  - Якщо Title порожній при спробі відправки → поле підсвічується червоним, під інпутом виводиться обов'язковий текст помилки: "Title is required" (виклик T-04).
  - Якщо Description порожній при спробі відправки → поле підсвічується червоним, виводиться текст: "Description is required".
  - Якщо користувач намагається ввести більше 50 символів у Title → ввід блокується на 50-му символі або виводиться текст помилки: "Title cannot exceed 50 characters". [APPROVED: D-09]
- **Error state:** Бекенд повертає помилку збереження (500) → текст над кнопками: "Failed to create issue. Try again.".

#### 5. Transitions

- **Incoming:** T-02 (із будь-якого стану S-02).
- **Outgoing:** T-03 (до попереднього стану S-02), T-04 (залишається у M-01 через помилку), T-05 (до S-02-A після успішного збереження).

#### 6. Рівні верифікації

- **У макеті (Figma):** Візуалізація обов'язковості полів (зірочки *), відображення повідомлення "Title is required", розміщення кнопок Create/Cancel.
- **У прототипі (Clickable):** Клік Create з порожнім інпутом показує фрейм помилки валідації; заповнений інпут закриває модалку та веде на оновлений список.
- **Лише в реалізації:** Фіксація точного автора з токена автентифікації, автоматична генерація унікального ID та timestamp.

### S-03: Issue Details Screen

#### 1. ID, призначення, actors, entry conditions

- **ID:** S-03
- **Призначення:** Детальний перегляд інформації про заявку, виконання дозволених змін статусів (виключно призначеним Assignee згідно з AC-07.4, DEF-01, D-10), призначення виконавця та пріоритету (лише Team Lead згідно з US-03, US-04, D-04), додавання та перегляд коментарів.
- **Actors:** Team Member, Team Lead.
- **Entry conditions:** Клік по рядку заявки на екрані S-02 (перехід T-06).

#### 2. Visible data

- **Issue ID:** Обов’язкове. Відображення ідентифікатора.
- **Title:** Обов’язкове. Текстова назва проблеми.
- **Description:** Обов’язкове. Повний опис дефекту.
- **Author:** Обов’язкове. Ім'я користувача, який створив заявку.
- **Created at:** Обов’язкове. Дата та час створення у форматі YYYY-MM-DD HH:mm.
- **Status:** Обов’язкове. Поточний статус (Open, In Progress, Resolved, Closed).
- **Priority:** Обов’язкове. Значення: Low, Normal, High, Critical. Вигляд відсутнього значення: нейтральний контурний бейдж "Not Set" (#D1D5DB). [APPROVED: D-03]
- **Assignee:** Необов’язкове. Вигляд відсутнього значення: "—" (Unassigned).
- **Comments List:** Стрічка коментарів. Для кожного коментаря обов’язково відображаються:
  - **Comment Author:** Обов’язкове.
  - **Comment Date/Time:** Обов’язкове.
  - **Comment Text:** Обов’язкове.
  - *Вигляд порожньої стрічки:* "No comments yet". [APPROVED: D-03]

#### 3. Controls

- **C-03.1 |** Back to List Link/Button | Navigation Control | Visible: Always; Enabled: Always | Trigger: Click | Результат: Повернення до списку S-02 зі збереженням попереднього фільтра (виклик T-07, D-07).
- **C-03.2 |** Status Transition Selector | Dropdown / Select | Visible: Always; Enabled: Лише якщо поточний користувач == Assignee даного issue та статус != Closed (для інших користувачів рендериться як Read-Only бейдж без кнопок зміни згідно з AC-07.4, DEF-01, D-10) | Trigger: Вибір значення зі списку дозволених переходів | Результат: Вибір цільового статусу згідно з BR-08.1. [S1: AC-07.4, BR-08.1; DEF-01, D-10]
- **C-03.3 |** Apply Status Button | Secondary Action Button | Visible: Лише для Assignee; Enabled: Коли в C-03.2 обрано новий валідний статус (для non-assignee прихована/disabled) | Trigger: Click | Результат: Фіксація нового статусу на сервері, оновлення поля Status на сторінці (виклики T-14, T-15, T-16, T-17). [S1: AC-07.4; DEF-01, D-06, D-10]
- **C-03.4 |** Assignee Selector | Dropdown / Select | Visible: Always; Enabled: Лише якщо актор = Team Lead (для Team Member — Disabled / Read-Only текст) | Trigger: Вибір члена команди (TL, TM1, TM2) або "— (Unassigned)" | Результат: Вибір виконавця або скидання поля (D-04).
- **C-03.5 |** Apply Assignee Button | Secondary Action Button | Visible & Enabled: Лише якщо актор = Team Lead (для Team Member повністю прихована) | Trigger: Click | Результат: Збереження нового виконавця або очищення поля (виклики T-10, T-11). Для Team Member недоступна (блокування T-12, D-05).
- **C-03.6 |** Priority Selector | Dropdown / Select | Visible: Always; Enabled: Лише якщо актор = Team Lead (для Team Member — Disabled / Read-Only текст) | Trigger: Вибір із допустимих встановлених значень (Low, Normal, High, Critical) | Результат: Вибір нового значення пріоритету (без опції Not Set згідно з D-03).
- **C-03.7 |** Apply Priority Button | Secondary Action Button | Visible & Enabled: Лише якщо актор = Team Lead (для Team Member повністю прихована) | Trigger: Click | Результат: Збереження пріоритету, оновлення відображення бейджа (виклик T-13). Для Team Member недоступна (блокування T-12, D-05).
- **C-03.8 |** Comment Input Area | Textarea | Visible: Always; Enabled: Always | Trigger: Введення тексту | Результат: Введення тексту обговорення проблеми.
- **C-03.9 |** Send Comment Button | Primary Action Button | Visible: Always; Enabled: Коли поле C-03.8 містить хоча б 1 непорожній символ (Disabled при порожньому тексті) | Trigger: Click | Результат: Перевірка обов'язковості тексту, відправка на бекенд, оновлення стрічки (виклики T-19, T-20).

#### 4. States

- **Default state:** Відображення завантажених параметрів заявки; поля введення коментаря порожні; кнопки Apply неактивні (до моменту зміни значень у селекторах).
- **Role-based states:**
  - **Team Lead View:** Селектори Assignee та Priority активні; кнопки Apply (C-03.5, C-03.7) доступні. Селектор Status активний лише якщо Team Lead є призначеним Assignee даної заявки; якщо заявка призначена на Team Member, статус відображається як заблокований Read-only бейдж згідно з AC-07.4, DEF-01, D-10.
  - **Team Member View:** Селектори Assignee та Priority відображаються як статичний Read-Only текст; кнопки дій Apply відсутні в макеті. Селектор Status активний лише якщо даний Member є поточним Assignee.
- **Closed issue state:** Якщо поточний статус заявки Closed, контрол вибору статусу C-03.2 блокується (Disabled), кнопка Apply Status прихована/заблокована. Жодні вихідні переходи статусів не пропонуються (термінальний стан).
- **Validation & Error states:**
  - Спроба відправки порожнього коментаря → кнопка Send Comment заблокована (Disabled).
  - Failed save коментаря (AC-06.5): Сервер повернув помилку збереження коментаря → коментар НЕ додається до списку; введений текст залишається у полі C-03.8; під полем виводиться текст помилки: "Failed to save comment. Please try again." (виклик T-20).

#### 5. Transitions

- **Incoming:** T-06 (з екрана S-02-A або S-02-B).
- **Outgoing:**
  - T-07 → повернення до S-02-A або S-02-B зі збереженням фільтра.
  - T-10, T-11, T-13, T-14, T-15, T-16, T-17, T-19 → успішне локальне оновлення даних на S-03.
  - T-12, T-14a, T-18, T-20 → збереження стану S-03 без зміни сутностей / блокування невалідних дій / відображення помилки.

#### 6. Рівні верифікації

- **У макеті (Figma):** Роздільне відображення екрана для ролей TL та TM (наявність/відсутність контролів Assignee та Priority; статусний селектор доступний лише призначеному Assignee); стан Failed save для коментаря; блокування статусів для Closed.
- **У прототипі (Clickable):** Клік на Apply Status змінює значення бейджа; клік на Back to List повертає у відповідний таб списку; клік на неактивні зони не дає переходу.
- **Лише в реалізації:** Серверна перевірка прав ролі (захист API від підробки запитів на пріоритет від Team Member або статусу від non-assignee), транзакційність запису коментарів.

## 2. Матриця прав доступу (Permission Matrix)

Матриця враховує дві базові глобальні ролі (Team Member, Team Lead) та контекстне відношення користувача до конкретного issue (Assignee чи Non-assignee).

Примітка щодо зміни статусу: Відповідно до вихідної вимоги AC-07.4 та затвердженого виправлення DEF-01 (скасування застарілої пропозиції AD-01), право зміни статусу належить суворо призначеному виконавцю (Assignee Only). Користувач, який не є виконавцем (включно з Team Lead, якщо він не призначив самого себе), не має права змінювати статус заявки (селектор заблокований або відображається статичний бейдж). Зміна здійснюється виключно за 4 дозволеними переходами матриці BR-08.1.

## 3. Матриця переходів статусів (Status Transition Matrix)

Поточний статус є поточним станом сутності і НЕ є переходом (перехід у самого себе відсутній).Статус Closed є кінцевим термінальним станом і НЕ має вихідних переходів.Усі переходи, не зазначені як «Дозволено», є неприпустимими та блокуються логікою інтерфейсу.

| Поточний статус (From) | Цільовий: Open | Цільовий: In Progress | Цільовий: Resolved | Цільовий: Closed | Коментар / Обґрунтування |
|---|---|---|---|---|---|
| Open | — (поточний) | ДОЗВОЛЕНО (T-14) | ЗАБОРОНЕНО | ЗАБОРОНЕНО | Старт робіт над дефектом (потрібен Assignee) |
| In Progress | ЗАБОРОНЕНО | — (поточний) | ДОЗВОЛЕНО (T-15) | ЗАБОРОНЕНО | Фіксація вирішення проблеми |
| Resolved | ЗАБОРОНЕНО | ДОЗВОЛЕНО (T-17) | — (поточний) | ДОЗВОЛЕНО (T-16) | Дозволено повторне відкриття роботи (Reopen) або остаточне закриття |
| Closed | ЗАБОРОНЕНО | ЗАБОРОНЕНО | ЗАБОРОНЕНО | — (термінальний) | Термінальний стан; вихідні дії відсутні |

## 4. Специфікація предиката "Important Issues"

Точний логічний предикат:$$\text{IsImportant} = (\text{Priority} \in \{\text{High}, \text{Critical}\}) \land (\text{Status} \neq \text{Closed})$$[SOURCE: US-08 (AC-08.1–AC-08.4), BR-09, BR-09.1; APPROVED: AD-03]Приклади обчислення предиката:

| Стан заявки (Priority + Status) | Результат предиката | Відображення у фільтрі Important | Обґрунтування / Бізнес-правило |
|---|---|---|---|
| High + Resolved | TRUE | ВІДОБРАЖАЄТЬСЯ | High ∈ {High, Critical}, а Resolved ≠ Closed. Згідно з BR-09.1, заявка зі статусом Resolved є вирішеною, але не закритою, тому залишається активною. |
| Critical + Closed | FALSE | НЕ ВІДОБРАЖАЄТЬСЯ | Статус дорівнює Closed. Згідно з AC-08.4, закриті заявки виключаються безумовно, незалежно від рівня пріоритету. |
| Not Set + Open | FALSE | НЕ ВІДОБРАЖАЄТЬСЯ | Not Set ∉ {High, Critical}. Відсутність встановленого пріоритету не дає підстав вважати заявку важливою. |
| Normal + In Progress | FALSE | НЕ ВІДОБРАЖАЄТЬСЯ | Згідно з AC-08.3, заявки з пріоритетами Low або Normal ніколи не потрапляють у список Important Issues. |
| Critical + In Progress | TRUE | ВІДОБРАЖАЄТЬСЯ | Обидві частини умови виконані: Critical та активний статус. |

## 6. Тестові сценарії для розробників та тестувальників (Test Cases)

Правило верифікації: Жоден тест нижче не отримує статус PASS наперед. Кожен сценарій фіксує передумову, дію, очікуваний візуальний результат та обмеження (що саме тест не здатний довести).

### TC-01: Створення заявки з валідними даними
- **Actor / Context:**  Будь-який автентифікований користувач (наприклад, Team Member 1).
- **Precondition:**  Відкрито модальне вікно M-01.
- **Action:**  У поле Title ввести "Critical bug in billing", у поле Description ввести "Crash on submit", натиснути кнопку Create (C-01M.3).
- **Expected visible result:**  Модальне вікно закривається. Відбувається перехід на S-02-A. У першому рядку списку з'являється новий issue: згенерований ID, Title = "Critical bug in billing", Status = "Open", Priority = "Not Set", Assignee = "—".
- **Що НЕ МОЖНА довести цим тестом:**  Не можна довести унікальність згенерованого ID на рівні бази даних та збереження точного серверного timestamp у бекенді без перевірки API.

### TC-02: Валідація обов'язковості поля Title
- **Actor / Context:**  Team Member або Team Lead.
- **Precondition:**  Відкрито модальне вікно M-01. Поле Title порожнє.
- **Action:**  Заповнити поле Description текстом "Some description", залишити Title порожнім і натиснути кнопку Create (C-01M.3).
- **Expected visible result:**  Модальне вікно M-01 залишається відкритим. Нова заявка не створюється. Поле Title підсвічується червоним контуром, під інпутом з'являється текст повідомлення про помилку: "Title is required".
- **Що НЕ МОЖНА довести цим тестом:**  Не можна довести поведінку валідації при передачі пробілів (whitespaces) або спеціальних символів без додаткового тестування обрізки рядків (trimming).

### TC-03: Валідація обов'язковості поля Description
- **Actor / Context:**  Team Member або Team Lead.
- **Precondition:**  Відкрито модальне вікно M-01.
- **Action:**  Ввести в поле Title валідний текст, залишити поле Description порожнім, натиснути Create (C-01M.3).
- **Expected visible result:**  Модальне вікно M-01 не закривається. Під полем Description з'являється повідомлення про помилку валідації: "Description is required".
- **Що НЕ МОЖНА довести цим тестом:**  Не можна довести підтримку або відхилення форматування переносу рядків (multiline carriage return).

### TC-04: Відображення списку зареєстрованих issues
- **Actor / Context:**  Team Member або Team Lead.
- **Precondition:**  У системі є раніше створені заявки. Користувач перейшов на S-02-A.
- **Action:**  Візуальний огляд таблиці списку.
- **Expected visible result:**  Таблиця містить стовпці: ID, Title, Status, Priority, Assignee. Для кожної заявки відображено її поточні параметри. Якщо у заявки не встановлено пріоритет, відображається текст "Not Set". Якщо не призначено виконавця, відображається прочерк "—".
- **Що НЕ МОЖНА довести цим тестом:**  Не можна довести порядок сортування за замовчуванням (по даті чи ID), оскільки критерій сортування не специфікований у вихідних вимогах.

### TC-05: Перегляд деталей існуючої заявки
- **Actor / Context:**  Team Member або Team Lead.
- **Precondition:**  Користувач перебуває на S-02-A, у списку відображається заявка ID: 101.
- **Action:**  Клікнути по рядку заявки ID: 101 (C-02.4).
- **Expected visible result:**  Відбувається перехід на екран S-03. На екрані відображені поля: ID (101), Title, Description, Author, Created at, Status, Priority, Assignee та блок коментарів.
- **Що НЕ МОЖНА довести цим тестом:**  Не можна довести цілісність даних при одночасному паралельному редагуванні іншим користувачем (race conditions).

### TC-06: Відображення порожнього списку (Empty State)
- **Actor / Context:**  Будь-який автентифікований користувач.
- **Precondition:**  База даних чиста (не зареєстровано жодної заявки).
- **Action:**  Виконати вхід у систему через S-01.
- **Expected visible result:**  Відкривається стан S-02-C. Таблиця відсутня. По центру екрана виводиться текст: "No issues found. Create the first issue to get started." та активна кнопка Create Issue (C-02.3).
- **Що НЕ МОЖНА довести цим тестом:**  Не можна довести швидкість завантаження Empty State при повільному 3G-з'єднанні.

### TC-07: Призначення виконавця та Unassign користувачем Team Lead
- **Actor / Context:**  Team Lead на екрані S-03.
- **Precondition:**  Заявка не має виконавця (Assignee = "—").

- **Що НЕ МОЖНА довести цим тестом:**  Не можна довести відправку поштового чи push-сповіщення призначеному користувачу (повідомлення out of scope).

- **Actor / Context:**  Будь-який автентифікований користувач на екрані S-03.
- **Precondition:**  Імітація збою мережі або бекенду (Mock 500 error при відправці коментаря).
- **Action:**  Ввести текст "Important note", натиснути Send Comment (C-03.9).
- **Expected visible result:**  Коментар НЕ з'являється у стрічці коментарів. Введений текст "Important note" зберігається в інпуті C-03.8. Над/під полем виводиться текст повідомлення: "Failed to save comment. Please try again.".
- **Що НЕ МОЖНА довести цим тестом:**  Не можна довести повторну автоматичну відправку (retry policy), оскільки вона не закладена у вимоги.

### TC-13: Дозволений перехід статусу Open → In Progress
- **Actor / Context:**  Автентифікований користувач, який є призначеним Assignee даної заявки (згідно з AC-07.4, DEF-01).
- **Precondition:**  Заявка має статус Open; виконавець попередньо призначений (Assignee != Not Set, DEF-02).
- **Action:**  Відкрити селектор статусів C-03.2, обрати "In Progress", натиснути Apply Status (C-03.3).
- **Expected visible result:**  Статус заявки змінюється на "In Progress". Бейдж статусу оновлюється. При повторному відкритті селектора статус Open більше недоступний.
- **Що НЕ МОЖНА довести цим тестом:**  Не можна довести автоматичну фіксацію користувача як виконавця (Assignee призначається окремо Team Lead).

### TC-14: Блокування неприпустимих переходів статусів (Strict State Machine)
- **Actor / Context:**  Будь-який користувач на екрані S-03.
- **Precondition:**  Заявка перебуває у статусі Open.
- **Action:**  Відкрити список варіантів у селекторі статусів C-03.2.
- **Expected visible result:**  У випадному списку присутній виключно один доступний цільовий варіант: "In Progress". Варіанти "Resolved" та "Closed" відсутні у списку (або є сірими/disabled). Перехід Open → Resolved чи Open → Closed неможливо ініціювати.
- **Що НЕ МОЖНА довести цим тестом:**  Не можна довести валідацію на рівні збереження стану в СУБД (CHECK constraint) без тесту схеми бази даних.

### TC-15: Фільтрація Important Issues (High/Critical та не Closed)
- **Actor / Context:**  Будь-який користувач на екрані S-02.
- **Precondition:**  У системі є 5 заявок:
  - Issue 1: Priority High, Status Open.
  - Issue 2: Priority Critical, Status Resolved.
  - Issue 3: Priority Critical, Status Closed.
  - Issue 4: Priority Low, Status In Progress.
  - Issue 5: Priority Not Set, Status Open.
- **Action:**  На екрані S-02 натиснути таб фільтра Important Issues (C-02.2).
- **Expected visible result:**  Екран переходить у стан S-02-B. У таблиці залишаються рівно дві заявки: Issue 1 (High + Open) та Issue 2 (Critical + Resolved). Заявки Issue 3 (Closed), Issue 4 (Low), Issue 5 (Not Set) повністю приховані зі списку.
- **Що НЕ МОЖНА довести цим тестом:**  Не можна довести поведінку системи при зміні пріоритету заявки у фоновому режимі іншим користувачем без ручного оновлення фільтра (відсутність WebSockets).

### TC-16: Валідація максимальної довжини Title (50 символів)
- **Actor / Context:**  Будь-який користувач у модальному вікні M-01.
- **Precondition:**  Відкрито форму створення заявки.
- **Action:**  Спробувати ввести в поле Title (C-01M.1) рядок довжиною 55 символів (наприклад, 55 літер "A").
- **Expected visible result:**  Інпут блокує введення на 50-му символі (в полі залишається рівно 50 символів) або під інпутом з'являється текст помилки/лічильник: "Title cannot exceed 50 characters".
- **Що НЕ МОЖНА довести цим тестом:**  Не можна довести поведінку при вставці спеціальних Unicode емодзі (де 1 символ може займати більше 1 байта/графемного кластера).
