4. ТЕКСТ ДЛЯ РОЗДІЛУ 9 СПЕЦИФІКАЦІЇ SD_Spec.docx (ДОДАТОК C4)
------------------------------------------------------------------------
Вхід:
  Погоджений Release Scope (US-01..US-08), 33 критерії приймання (AC),
  UI-релевантні бізнес-правила (BR-01..BR-12), системні NFR та журнал погоджених
  UX-рішень (D-01..D-08, AD-01..AD-09).
Робота:
  Сформувати перевірений аналітичний Input Pack; спланувати мінімальну систему
  поверхонь та сценаріїв переходу; провести верифікацію контрактів розробником
  (Plan Review); усунути виявлені виклики логіки прав (DEF-01, DEF-02);
  створити редаговані Low-Fidelity wireframes засобами AI та ручної збірки;
  виконати клікабельне прототипування основних сценаріїв та провести підсумковий аудит доказів.
Вихід:
  Screen Map + Developer-Verifiable Screen Contracts + Low-Fi Wireframes у Figma +
  Клікабельний прототип + Матриця Traceability + Підсумковий Review/Defect/Change Log.
Критерій завершення:
  Дизайн покриває 100% включених функціональних вимог першого релізу;
  критичні дефекти та блокери відсутні; межі доказовості статичного інтерфейсу
  та прототипу задокументовані.


5. РЕКОМЕНДОВАНА СТРУКТУРА ВІДЕОЗВІТУ ДЛЯ ЗАОЧНОГО ЗАХИСТУ (§22)
------------------------------------------------------------------------
Загальний хронометраж: 4.5 – 6 хвилин.
1. Частина 1 (30 с): Бригада, матеріали та розподіл обов'язків.
   - Назвати учасників, версію специфікації SD_Spec.docx та посилання на фінальний макет.
2. Частина 2 (1 – 1.5 хв): Спільний результат та наскрізний сценарій.
   - Демонстрація структури екранів у Figma.
   - Проходження флоу в Prototype: Issues List -> Create Modal -> Issue Details -> Back.
   - Оголошення дій, які симулюються у прототипі.
3. Частина 3 (30 с на учасника): Особистий внесок.
   - Кожен учасник показує конкретний артефакт: Input Pack, контракт, компонент чи тест.
   - Пояснити, що згенерував AI, а що перевірив або виправив студент.
4. Частина 4 (30 с – 1 хв на учасника): Від вимоги до рішення.
   - Показати зв'язок на одному прикладі: вихідний AC у SD_Spec -> контракти -> елемент макета.
5. Частина 5 (1 – 1.5 хв на учасника): Індивідуальне контрольне завдання.
   - Розібрати тестовий кейс (наприклад: чому ISS-003 Resolved є у Important, або блокування статусу для не-виконавця).
6. Частина 6 (30 с – 1 хв): Підсумок перевірки та межі результату.
   - Звіт журналу дефектів (що виправлено, що залишилося для бекенду).
   - Чітке розмежування макета від серверної реалізації (HTTPS, бекапи, БД).
