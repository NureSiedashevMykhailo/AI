## 1. Мета роботи та короткий опис виконаних завдань

**Мета роботи**: Навчитися застосовувати AI-асистента для критичного аналізу, виявлення неоднозначностей та формалізації вимог замість неконтрольованого генерування документації; перетворити неповний запит замовника на верифіковану технічну специфікацію, архітектуру та REST API контракт, придатні для безпосередньої реалізації в ЛР2 та автоматизованого тестування в ЛР3.

**Виконані завдання**:
1. Проведено первинний інженерний аналіз вихідного запиту замовника та виділено межі проєкту (`FR-01–FR-07`, а також відкладену вимогу `FR-08` для ЛР4) у файлі [docs/requirements.md](requirements.md).
2. Виконано критичний діалог з AI-асистентом для пошуку «сліпих зон» (нормалізація рядків, семантика часткового оновлення, граничні стани фільтрації, пріоритет перевірок помилок), відсіяно позапланові пропозиції моделі та задокументовано хід роботи у [docs/ai-log.md](ai-log.md).
3. Сформульовано 7 перевірюваних User Stories (`US-01–US-07`) із позитивними, граничними та негативними критеріями приймання у форматі *Given / When / Then* та 4 нефункціональні вимоги (`NFR-01–NFR-04`) із чіткими методами верифікації.
4. Спроєктовано чотиришарову архітектуру сервісу (`Routes`, `Schemas`, `Service`, `Repository/SQLite`) з точкою розширення `ClassifierService (Stub)`, побудовано ER-модель сутностей (`User`, `Issue`, `Comment`) та зафіксовано архітектурні рішення `ADR-01` і `ADR-02` у [docs/architecture.md](architecture.md).
5. Узгоджено повний контракт для 9 REST API маршрутів із прикладами запитів, успішних відповідей та помилок (`404`, `409`, `422`) у [docs/api-contract.md](api-contract.md).
6. Побудовано наскрізну матрицю простежуваності вимог до майбутніх `pytest`-тестів у [docs/traceability.csv](traceability.csv).

## 2. Ключові інженерні рішення та уточнення вимог

Усі бізнес-правила централізовані в єдиному джерелі істини — [docs/requirements.md](requirements.md). Нижче наведено три фундаментальні рішення, що усунули неоднозначності початкової постановки:

### 2.1. Жорстка семантика часткового оновлення (`PATCH`) та транзакційна атомарність
У вимозі `FR-03` зазначено, що клієнт передає лише ті поля, які потрібно змінити, а `FR-05` дозволяє знімати виконавця через `null`. Для уникнення конфлікту типів у [docs/requirements.md (Розділ 6)](requirements.md#6-семантика-часткового-оновлення-patch) зафіксовано:
* **Ключ відсутній у JSON (`undefined` / `exclude_unset=True`)**: поле не змінюється, зберігається поточне значення в БД.
* **Ключ передано зі значенням `null`**: дозволено **виключно** для `assignee_id` (зняття призначення виконавця). Передача `null` для `title`, `description` або `priority` негайно відхиляється зі статусом `422 Unprocessable Entity`.
* **Порожній об'єкт `{}`**: для відкритої заявки (`OPEN`, `IN_PROGRESS`) трактується як валідна ідемпотентна операція (`no-op`), що повертає `200 OK` без модифікації БД; для закритої заявки повертає `409 Conflict`.
* **Атомарний відкат**: якщо в одному `PATCH`-запиті передано одночасно коректне поле (наприклад, валідний `title`) і некоректне (наприклад, неіснуючий `assignee_id: 99`), вся операція відхиляється (`422`), і жодна зміна не зберігається в SQLite.

### 2.2. Матриця переходів статусів $3 \times 3$ та регламент закритої заявки (`CLOSED`)
Текстові правила замовника перетворено на повну детерміновану матрицю $3 \times 3$ у [docs/requirements.md (Розділ 5)](requirements.md#5-життєвий-цикл-заявки-та-матриця-переходів):
* **Дозволені переходи (`200 OK`)**: `OPEN → IN_PROGRESS`, `OPEN → CLOSED` (пряме закриття без проміжного етапу), `IN_PROGRESS → CLOSED`.
* **Ідемпотентні переходи (`200 OK` без змін)**: встановлення вже поточного статусу (`OPEN → OPEN`, `IN_PROGRESS → IN_PROGRESS`, `CLOSED → CLOSED`) не вважається помилкою.
* **Заборонені переходи (`409 Conflict`)**: будь-яке повернення назад (`IN_PROGRESS → OPEN`, `CLOSED → OPEN`, `CLOSED → IN_PROGRESS`).
* **Режим статусу `CLOSED`**: закрита заявка є незмінною (immutable) щодо основних атрибутів (`title`, `description`, `priority`, `assignee_id` — будь-який виклик `PATCH /issues/{id}` блокується кодом `409 Conflict`), проте залишається відкритою для читання (`GET /issues/{id}`) та додавання нових коментарів (`POST /issues/{id}/comments`).

### 2.3. Ізоляція тестового середовища через SQLite та автономність від зовнішніх сервісів
Згідно з `ADR-01` та `ADR-02` ([docs/architecture.md, Розділ 3](architecture.md#3-архітектурні-рішення-architecture-decision-records)):
* Використання вбудованої СУБД SQLite забезпечує нульовий поріг локального запуску (`NFR-01`) та дозволяє підміняти робочу БД (`app.db`) на ізольовану базу в оперативній пам'яті (`sqlite:///:memory:`) під час запуску `pytest` (`NFR-02`).
* Точка інтеграції AI (`ClassifierService`) відокремлена від бізнес-логіки й транзакцій БД та в ЛР1–ЛР3 реалізується як детермінований Stub, що гарантує 100% працездатність трекера без підключення до LLM (`NFR-04`).

## 3. Показові випадки критичного використання AI та верифікації результатів

Повний реєстр запитів зафіксовано в [docs/ai-log.md](ai-log.md). Нижче наведено два показові кейси критичної оцінки пропозицій AI:

### Кейс 1: Відхилення галюцинацій скоупу (Статус `REOPENED`, пагінація та JWT-авторизація)
* **Контекст**: Під час первинного аналізу неоднозначностей (Запис 1 у [docs/ai-log.md](ai-log.md)) AI-асистент за шаблоном типових комерційних трекерів запропонував:
  1. Додати перехід `CLOSED → OPEN` (або статус `REOPENED`) на випадок повторного виявлення дефекту.
  2. Додати параметри пагінації `limit` та `offset` до маршруту `GET /issues`.
  3. Запровадити перевірку прав доступу через JWT-токени для розмежування авторів і виконавців.
* **Критична оцінка та перевірка**: Звірка з Розділом 2 («Що не входить до обов’язкового обсягу») та Розділом 3 («Правила роботи із заявками») показала, що всі три пропозиції є прямим порушенням умов завдання (`[Зайва функція]` та `[Суперечність рішенню замовника]`). Два користувачі (`1 — Agent A`, `2 — Agent B`) є синтетичним тестовим довідником, а повернення із закритого стану прямо заборонено.
* **Рішення**: Усі три пропозиції **повністю відхилено**. У специфікації закріплено незворотність `CLOSED` (`409 Conflict`) та роботу без автентифікації й пагінації.

### Кейс 2: Прийняття формалізації валідації (`trim` для коментарів та `extra = "forbid"`)
* **Контекст**: Під час опрацювання правил валідації (Запис 2 у [docs/ai-log.md](ai-log.md)) модель вказала на прогалину: для `title` вимога видалення крайніх пробілів (`trim`) прописана явно, а для тексту коментаря вказано лише «непорожній текст до 1000 символів». Без попереднього `trim` рядок із самих пробілів `"   "` пройшов би перевірку `len > 0`. Також було запропоновано правило `extra = "forbid"` для `PATCH /issues/{id}`.
* **Критична оцінка та перевірка**: Перевірено на відповідність бізнес-правилам Розділу 3: збереження порожнього коментаря з пробілів порушує вимогу змістовності коментарів, а передача поля `status` у загальний `PATCH /issues/{id}` порушує вимогу `FR-03` про окрему операцію зміни статусу.
* **Рішення**: Пропозиції **прийнято** як `[Корисне уточнення форми]` та внесено до контракту схем Pydantic ([docs/requirements.md, Розділ 4.1 та 6](requirements.md#41-специфікація-сутностей-і-полів)).

## 4. Результати перехресного рев'ю специфікації (Cross-Review)

Перед фіксацією API-контракту проведено перехресну верифікацію узгодженості між [docs/requirements.md](requirements.md), [docs/architecture.md](architecture.md) та [docs/api-contract.md](api-contract.md):

1. **Усунення розбіжності переліку полів у `PATCH /issues/{id}`**: У короткому описі `FR-03` згадувалися лише `title`, `description`, `priority`, тоді як `FR-05` вимагав призначення та зняття виконавця (`assignee_id`). Під час рев'ю контракти синхронізовано: `assignee_id` офіційно включено до тіла `PATCH /issues/{id}` (а окремий ендпоінт залишено виключно для `PATCH /issues/{id}/status`).
2. **Детермінований порядок перевірок та розмежування кодів `404 / 409 / 422`**: Усунено неоднозначність, який код повертати при комбінованій помилці (наприклад, невалідне тіло запиту до неіснуючої або закритої заявки). Встановлено суворий конвеєр:
   $$\text{1. Схема входу (422)} \longrightarrow \text{2. Існування запису в БД (404)} \longrightarrow \text{3. Допустимість стану / переходу (409)}$$
3. **Граничні випадки вибірки та сортування**: Перевірено, що пустий результат фільтрації `GET /issues?status=...&priority=...` повертає `200 OK` із `[]` (а не `404`), а хронологічний порядок створення детерміновано захищений вторинним ключем `ORDER BY created_at ASC, id ASC`.

## 5. Метрика простежуваності вимог (Traceability Coverage)

У файлі [docs/traceability.csv](traceability.csv) кожну обов'язкову функціональну вимогу (`FR-01–FR-07`) пов'язано наскрізним ланцюжком із User Story, критеріями приймання (`AC`), архітектурним компонентом / маршрутом API та назвою майбутнього автоматизованого тесту `pytest`:

$$\text{Coverage} = \frac{\text{Кількість покритих вимог (FR-01..FR-07)}}{\text{Загальна кількість обов'язкових вимог MVP}} \times 100\% = \frac{7}{7} \times 100\% = 100.0\%$$

*(Відкладена вимога `FR-08` зафіксована окремим рядком із позначкою `Future / LR4` і точкою розширення `ClassifierService (Stub)`).*

## 6. Висновки

1. Використання AI-асистента у режимі критичного діалогу дозволило виявити приховані крайові умови (семантика `missing` vs `null` у `PATCH`, пробільні рядки, колізії таймстемпів при сортуванні) ще до написання коду.
2. Чітка фіксація меж обсягу (Out of Scope) захистила архітектуру від ускладнення зайвими підсистемами (JWT-автентифікація, пагінація, кастомні статуси), які AI пропонує за інерцією.
3. Отримана специфікація є повністю детермінованою та перевірюваною: кожне бізнес-правило має однозначне відображення у HTTP-статусах (`200`, `201`, `404`, `409`, `422`) і готовий сценарій перевірки для ЛР2–ЛР3.
