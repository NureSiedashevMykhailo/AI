# Mini Issue Tracker — Специфікація вимог та бізнес-правил
**Версія**: 1.0 (APPROVED)  
**Статус**: Єдине джерело істини (Single Source of Truth)  
**Цільовий стек**: Python 3.11+, FastAPI, SQLite, Pydantic v2, pytest  

---

## 1. Межі проєкту та функціональні вимоги (Scope)

### 1.1. Включено до обов'язкового обсягу (MVP)
* **FR-01 (Створення заявки)**: Створення заявки з обов'язковою назвою (`title`) та необов'язковим описом (`description`). Початковий статус — строго `OPEN`. Пріоритет за замовчуванням — `medium`.
* **FR-02 (Перегляд та фільтрація)**: Отримання списку заявок та детальної інформації про конкретну заявку за її ідентифікатором. Фільтрація за параметрами `status` та `priority` окремо та сумісно (зв'язка через логічне `AND`). Відсутність результатів повертає пустий список `[]`.
* **FR-03 (Часткове редагування)**: Редагування заявки як часткове оновлення (`PATCH`). Клієнт передає лише ті поля, які змінюються (`title`, `description`, `priority`, `assignee_id`). Зміна статусу винесена в окрему операцію.
* **FR-04 (Керування статусом)**: Життєвий цикл керується строгою матрицею станів. Спроби некоректних переходів відхиляються без зміни даних. Повторне встановлення поточного статусу є ідемпотентним.
* **FR-05 (Призначення виконавця)**: Призначення або зняття виконавця. Дозволений фіксований довідник: користувачі `1` (`Agent A`) та `2` (`Agent B`). Значення `null` знімає призначення.
* **FR-06 (Коментарі)**: Додавання та перегляд коментарів до існуючої заявки від одного з двох відомих користувачів. Дозволено додавати коментарі до закритих заявок.
* **FR-07 (Збереження та валідація)**: Збереження стану в реляційній базі SQLite. Забезпечення персистентності між перезапусками сервісу. Атомарна валідація вхідних даних на рівні схем.
* **FR-08 (AI-рекомендації — Резерв для ЛР4)**: Дорадча класифікація (категорія, пріоритет, резюме). Не модифікує сутності автоматично і не входить до реалізації в ЛР1–ЛР3.

### 1.2. Виключено з обов'язкового обсягу (Explicitly Out of Scope)
* Реєстрація, автентифікація, паролі, токени (JWT/OAuth), сесії.
* Рольова модель доступу (RBAC). Два користувачі `1` та `2` виступають синтетичним довідником, передача ID не є підтвердженням особи.
* Видалення заявок (будь-яке: фізичне або soft delete).
* Пагінація (`limit`, `offset`, курсори).
* Повнотекстовий пошук, вкладення файлів (attachments), email-сповіщення.
* Docker, хмарне розгортання, окремі векторні бази даних.

### 1.3. Журнал уточнень вимог (Рішення замовника vs Технічні рішення автора)

| Питання / Неоднозначність | Джерело рішення | Прийняте правило | Обґрунтування |
| :--- | :--- | :--- | :--- |
| Життєвий цикл статусів і закриті заявки | Рішення замовника (Розділ 3) | Переходи тільки вперед (`OPEN → IN_PROGRESS → CLOSED`, `OPEN → CLOSED`); `CLOSED` не редагується (`409`), але доступний для читання й коментарів. | Пряма бізнес-заборона на повернення до попередніх статусів та зміну закритих заявок. |
| Призначення та зняття виконавця | Рішення замовника (Розділ 3) | Фіксований довідник `[1, 2]`; передача `assignee_id: null` у `PATCH /issues/{id}` знімає призначення. | Забезпечує повний цикл керування виконавцем без введення таблиці ролей або авторизації. |
| Семантика порожнього `PATCH {}` та невідомих полів | Технічне рішення автора (з AI) | Порожній `{}` на відкритій заявці є ідемпотентним `no-op` (`200 OK`); невідомі ключі відхиляються (`extra = "forbid"`, `422`). | Відповідність семантиці часткового оновлення та захист від друкарських помилок клієнта у назвах полів. |
| Черговість перевірок (`422 → 404 → 409`) | Технічне рішення автора (з AI) | Спочатку валідація схеми (`422`), далі перевірка існування запису (`404`), потім перевірка стану (`409`). | Відсікає синтаксично некоректні запити до звернення до БД і робить коди відповідей однозначними для автотестів. |
| Детермінований порядок сортування списків | Технічне рішення автора (з AI) | Усі вибірки заявок і коментарів впорядковуються за `ORDER BY created_at ASC, id ASC`. | Вторинний ключ `id ASC` гарантує стабільний порядок записів, створених в одну й ту саму частку секунди. |

## 2. Нефункціональні вимоги (NFR)

* **NFR-01 (Відтворюваний локальний запуск)**: Після стандартного встановлення залежностей застосунок та набір автотестів запускаються і працюють локально у віртуальному середовищі `venv` без доступу до інтернету та зовнішніх мережевих сервісів.  
  * *Спосіб перевірки*: Після виконання `pip install -r requirements.txt` у чистому `venv` запуск сервера та проходження `pytest` виконуються автономно за вимкненого мережевого з'єднання.
* **NFR-02 (Ізоляція тестової бази даних)**: Виконання тестів не зачіпає і не модифікує файл робочої бази даних SQLite (`app.db`).  
  * *Спосіб перевірки*: Автоматичні тести використовують фікстуру з виділеним тимчасовим файлом (`tmp_path / "test.db"` — зокрема для перевірки збереження даних між перезапусками) або базою в оперативній пам'яті (`sqlite:///:memory:`); хеш і час модифікації робочого файлу `app.db` до і після запуску `pytest` залишаються незмінними.
* **NFR-03 (Детерміновані структуровані помилки)**: Усі помилки валідації повертають HTTP-код `422 Unprocessable Entity` у стандартному JSON-форматі Pydantic із зазначенням локації поля та типу порушення. Помилки бізнес-правил повертають HTTP `409 Conflict`.  
  * *Спосіб перевірки*: Негативні інтеграційні тести перевіряють статус-код та структуру JSON-відповіді для некоректних запитів.
* **NFR-04 (Автономність базового обліку)**: Базовий контур обліку задач (FR-01–FR-07) функціонує повністю автономно без підключення до LLM чи зовнішніх AI API.  
  * *Спосіб перевірки*: Запуск та успішне проходження повного набору тестів для FR-01–FR-07 за повністю відключеного інтернет-з'єднання.

## 3. User Stories та критерії приймання (Acceptance Criteria)

### US-01: Створення нової заявки
* **Актор**: Користувач
* **Дія**: Створити нову заявку, вказавши назву, опис (опціонально), пріоритет (опціонально) та виконавця (опціонально).
* **Користь**: Щоб зареєструвати виявлену проблему в системі для подальшої обробки командою.
* **Зв'язок**: FR-01, FR-05, FR-07
* **Критерії приймання**:
  * **AC-01-01 (Позитивний)**: 
    * *Given* клієнт надсилає валідні дані: назва `"Fix payment gateway timeout"`, опис не передано, пріоритет не передано,
    * *When* виконується запит `POST /issues`,
    * *Then* сервер повертає статус `201 Created`, генерує унікальний цілий `id`, статус встановлює в `OPEN`, опис у `""`, пріоритет у `medium`, виконавця у `null`, фіксує поточний `created_at` у UTC.
  * **AC-01-02 (Негативний — валідація короткої назви)**:
    * *Given* клієнт передає назву `"  ab  "` (довжина 2 символи після видалення крайніх пробілів),
    * *When* виконується запит `POST /issues`,
    * *Then* сервер повертає `422 Unprocessable Entity`, запис у базу даних не вноситься.
  * **AC-01-03 (Позитивний — збереження даних після перезапуску сервісу)**:
    * *Given* створено заявку та коментар до неї у файловій базі SQLite,
    * *When* сервіс зупиняється і повторно запускається з тим самим файлом SQLite, після чого виконуються `GET /issues/{id}` та `GET /issues/{id}/comments`,
    * *Then* сервер повертає `200 OK`, а ідентифікатори, поля заявки та прив'язані коментарі зберігаються без втрат.

### US-02: Перегляд та фільтрація списку заявок
* **Актор**: Учасник команди
* **Дія**: Отримати список усіх заявок або відфільтрувати їх за статусом та/або пріоритетом.
* **Користь**: Щоб швидко знаходити релевантні задачі та оцінювати поточний беклог.
* **Зв'язок**: FR-02
* **Критерії приймання**:
  * **AC-02-01 (Позитивний — комбінована фільтрація AND)**:
    * *Given* у системі існують заявки з різними статусами та пріоритетами,
    * *When* виконується запит `GET /issues?status=OPEN&priority=high`,
    * *Then* сервер повертає `200 OK` та масив заявок, які одночасно мають `status == "OPEN"` **AND** `priority == "high"`, відсортовані за `created_at ASC, id ASC`.
  * **AC-02-02 (Граничний — фільтрація без збігів)**:
    * *Given* у системі немає заявок зі статусом `CLOSED` та пріоритетом `low`,
    * *When* виконується запит `GET /issues?status=CLOSED&priority=low`,
    * *Then* сервер повертає `200 OK` та порожній масив `[]` (повернення 404 заборонене).

### US-03: Перегляд однієї заявки за ідентифікатором
* **Актор**: Учасник команди
* **Дія**: Запитати детальні дані заявки за її ID.
* **Користь**: Щоб ознайомитися з повною інформацією про задачу перед початком роботи.
* **Зв'язок**: FR-02
* **Критерії приймання**:
  * **AC-03-01 (Позитивний)**:
    * *Given* у базі існує заявка з `id = 5`,
    * *When* виконується запит `GET /issues/5`,
    * *Then* сервер повертає `200 OK` та повний JSON-об'єкт цієї заявки.
  * **AC-03-02 (Негативний — неіснуючий ресурс)**:
    * *Given* у базі немає заявки з `id = 9999`,
    * *When* виконується запит `GET /issues/9999`,
    * *Then* сервер повертає `404 Not Found`.

### US-04: Часткове редагування атрибутів заявки
* **Актор**: Учасник команди
* **Дія**: Оновити окремі поля заявки (назву, опис, пріоритет або призначити/зняти виконавця).
* **Користь**: Щоб актуалізувати дані без ризику перезаписати паралельні зміни інших полів.
* **Зв'язок**: FR-03, FR-05, FR-07
* **Критерії приймання**:
  * **AC-04-01 (Позитивний — зняття виконавця та оновлення пріоритету)**:
    * *Given* відкрита заявка має `assignee_id = 1` та `priority = "low"`,
    * *When* виконується `PATCH /issues/{id}` з тілом `{"assignee_id": null, "priority": "high"}`,
    * *Then* сервер повертає `200 OK`, у базі виконавець стає `null`, пріоритет — `"high"`, а `title` та `description` залишаються незмінними.
  * **AC-04-02 (Негативний — атомарність при частково некоректних даних)**:
    * *Given* існує відкрита заявка,
    * *When* виконується `PATCH /issues/{id}` з тілом `{"title": "Valid New Title", "assignee_id": 99}` (комбінація валідного та невалідного полів),
    * *Then* API повертає `422 Unprocessable Entity`, а повторне читання заявки через `GET /issues/{id}` показує, що всі її поля (включаючи `title` та `assignee_id`) залишилися незмінними.
  * **AC-04-03 (Негативний — призначення невідомого виконавця)**:
    * *Given* існує відкрита заявка,
    * *When* виконується `PATCH /issues/{id}` з тілом `{"assignee_id": 99}` (користувач поза фіксованим довідником `[1, 2]`),
    * *Then* сервер повертає `422 Unprocessable Entity`, поточний виконавець заявки не змінюється.
  * **AC-04-04 (Позитивний — призначення відомого виконавця)**:
    * *Given* відкрита заявка має `assignee_id = null`,
    * *When* виконується `PATCH /issues/{id}` з тілом `{"assignee_id": 2}`,
    * *Then* сервер повертає `200 OK`, у базі виконавець змінюється на `2` (`Agent B`), а решта полів заявки (`title`, `description`, `priority`, `status`) залишаються незмінними.

### US-05: Керування життєвим циклом та зміна статусу
* **Актор**: Учасник команди
* **Дія**: Перевести статус заявки відповідно до регламенту життєвого циклу.
* **Користь**: Щоб коректно відображати стадію вирішення проблеми в команді.
* **Зв'язок**: FR-04
* **Критерії приймання**:
  * **AC-05-01 (Позитивний — допустимий перехід та ідемпотентність)**:
    * *Given* заявка перебуває у статусі `OPEN`,
    * *When* надсилається `PATCH /issues/{id}/status` з тілом `{"status": "IN_PROGRESS"}`,
    * *Then* статус змінюється на `IN_PROGRESS` (код `200 OK`), а повторне надсилання `{"status": "IN_PROGRESS"}` повертає `200 OK` без помилки.
  * **AC-05-02 (Негативний — спроба повернення з CLOSED)**:
    * *Given* заявка має статус `CLOSED`,
    * *When* надсилається `PATCH /issues/{id}/status` з тілом `{"status": "OPEN"}`,
    * *Then* сервер повертає `409 Conflict`, збережений статус залишається `CLOSED`.

### US-06: Захист закритої заявки від модифікації
* **Актор**: Учасник команди
* **Дія**: Спробувати відредагувати основні реквізити закритої заявки.
* **Користь**: Забезпечити незмінність історії та результатів виконаних робіт.
* **Зв'язок**: FR-03, FR-04
* **Критерії приймання**:
  * **AC-06-01 (Негативний — заборона PATCH основних даних)**:
    * *Given* заявка має статус `CLOSED`,
    * *When* виконується запит `PATCH /issues/{id}` для оновлення `description` або `priority`,
    * *Then* сервер повертає `409 Conflict`, дані в базі залишаються незмінними.
  * **AC-06-02 (Позитивний — збереження доступу на читання)**:
    * *Given* заявка має статус `CLOSED`,
    * *When* виконується запит `GET /issues/{id}`,
    * *Then* сервер повертає `200 OK` з актуальними даними закритої заявки.

### US-07: Додавання та перегляд коментарів
* **Актор**: Автор коментаря (користувач `1` або `2`)
* **Дія**: Додати текстовий коментар до існуючої заявки або переглянути стрічку обговорення.
* **Користь**: Щоб фіксувати результати технічного розслідування та хід виконання робіт.
* **Зв'язок**: FR-06
* **Критерії приймання**:
  * **AC-07-01 (Позитивний — коментування закритої заявки)**:
    * *Given* заявка має статус `CLOSED`,
    * *When* надсилається `POST /issues/{id}/comments` з валідними даними `author_id: 1` та непорожнім текстом,
    * *Then* сервер повертає `201 Created`, коментар зберігається і зв'язується із заявкою, встановлюється час `created_at` у UTC.
  * **AC-07-02 (Негативний — порожній коментар)**:
    * *Given* існує заявка у будь-якому статусі,
    * *When* надсилається `POST /issues/{id}/comments` з текстом `"   "` (порожній після trim),
    * *Then* сервер повертає `422 Unprocessable Entity`, коментар не зберігається.
  * **AC-07-03 (Позитивний — перегляд списку коментарів у хронологічному порядку)**:
    * *Given* до існуючої заявки додано кілька коментарів,
    * *When* виконується запит `GET /issues/{id}/comments`,
    * *Then* сервер повертає `200 OK` та JSON-масив коментарів, прив'язаних до цієї заявки (`issue_id`), відсортований у порядку створення (`ORDER BY created_at ASC, id ASC`).

### US-08: Консультативна AI-класифікація звернення (Future / LR4)
* **Актор**: Учасник команди
* **Дія**: Отримати автоматичну рекомендацію щодо категорії, пріоритету та короткого резюме заявки на основі її назви й опису.
* **Користь**: Щоб пришвидшити первинну оцінку звернення без ризику неконтрольованої зміни даних заявки.
* **Зв'язок**: FR-08 *(Резерв для ЛР4)*
* **Критерії приймання**:
  * **AC-08-01 (Позитивний — дорадча рекомендація без автозастосування, Future / LR4)**:
    * *Given* існує заявка з назвою та описом проблеми,
    * *When* запитується AI-рекомендація класифікатора,
    * *Then* система повертає структуру рекомендації (`category`, `suggested_priority`, `summary`), але збережені атрибути заявки (`priority`, `title`, `description`, `status`) не змінюються без окремого підтвердження користувачем через `PATCH /issues/{id}`.

## 4. Формалізований контракт даних та валідація

### 4.1. Специфікація сутностей і полів

#### Сутність `User` (Синтетичний довідник)
| Поле | Тип | Хто задає | Обов'язкове | Дефолт | Nullable | Валідація та межі | Зміна після створення |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| `id` | Integer (PK) | Система | Так | — | Ні | Допустимі значення строго `1` або `2` | Ні |

## 5. Життєвий цикл заявки та матриця переходів

### 5.1. Повна матриця переходів (3 × 3)

| Поточний стан | Запитано: `OPEN` | Запитано: `IN_PROGRESS` | Запитано: `CLOSED` |
| :--- | :--- | :--- | :--- |
| **`OPEN`** | **Ідемпотентно (200 OK)**<br>Стан уже встановлений, змін немає. | **Дозволено (200 OK)**<br>Перехід у роботу. | **Дозволено (200 OK)**<br>Пряме закриття задачі. |
| **`IN_PROGRESS`** | **Заборонено (409 Conflict)**<br>Повернення назад не передбачене. | **Ідемпотентно (200 OK)**<br>Стан уже встановлений, змін немає. | **Дозволено (200 OK)**<br>Успішне завершення. |
| **`CLOSED`** | **Заборонено (409 Conflict)**<br>Термінальний стан. Реопен заборонено. | **Заборонено (409 Conflict)**<br>Термінальний стан. Відновлення заборонено. | **Ідемпотентно (200 OK)**<br>Стан уже встановлений, змін немає. |

### 5.2. Регламент операцій для закритої заявки (`CLOSED`)
* `GET /issues/{id}` — **Дозволено**: перегляд історії збережених реквізитів.
* `POST /issues/{id}/comments` — **Дозволено**: додавання технічних коментарів пост-фактум.
* `GET /issues/{id}/comments` — **Дозволено**: перегляд стрічки коментарів.
* `PATCH /issues/{id}` — **Заборонено (409 Conflict)**: основні атрибути (`title`, `description`, `priority`, `assignee_id`) не підлягають модифікації після закриття.
* `PATCH /issues/{id}/status` — **Заборонено (409 Conflict)** (крім ідемпотентного запиту `{"status": "CLOSED"}`).

## 6. Семантика часткового оновлення (PATCH)

Операція `PATCH /issues/{id}` реалізує строгі правила обробки модифікацій:

1. **Відсутність ключа у JSON (undefined)**: Відповідне поле ігнорується, у базі даних зберігається поточне значення.
2. **Передача `null`**: Дозволена **виключно** для стовпця `assignee_id` (зняття призначення виконавця). Передача `null` для `title`, `description` або `priority` є валідаційним порушенням і повертає `422 Unprocessable Entity`.
3. **Порожній об'єкт `{}`**: Для відкритої заявки (`OPEN`, `IN_PROGRESS`) є валідною ідемпотентною операцією (`no-op`): повертає `200 OK` та поточний стан заявки без звернення до транзакції запису. Для закритої заявки повертає `409 Conflict`.
4. **Невідомі та заборонені поля**: Конфігурація схеми Pydantic використовує правило `extra = "forbid"`. Передача заборонених полів (`id`, `created_at`, `status`) або довільних ключів негайно викликає помилку `422 Unprocessable Entity`.
5. **Атомарність операції модифікації (дворівневий захист)**: Усі зміни в межах одного запиту застосовуються за принципом «все або нічого» (`all-or-nothing`):
   * *Атомарність на рівні вхідної схеми (API / Schemas)*: якщо комбінований запит містить хоча б одне невалідне поле (наприклад, валідний `title` та невалідний `assignee_id: 99`), весь пакет відхиляється Pydantic зі статусом `422 Unprocessable Entity` до звернення до БД, не зберігаючи жодної частини змін (`AC-04-02`).
   * *Транзакційна атомарність БД (Repository / SQLite)*: усі валідні зміни записуються в межах однієї транзакції; у разі збою під час запису в репозиторії виконується `rollback` сесії SQLite, що гарантує збереження початкових даних.

## 7. Каталог результатів та обробка виняткових ситуацій

### 7.1. Порядок виконання перевірок
Для усунення невизначеності сервер виконує перевірки запиту у фіксованому порядку:
1. **Синтаксис та відповідність схемі (Schemas / Pydantic)** $\rightarrow$ помилка викликає **`422 Unprocessable Entity`**.
2. **Існування цільової сутності в базі даних (Database)** $\rightarrow$ відсутність запису за ID викликає **`404 Not Found`**.
3. **Бізнес-правила та стан життєвого циклу (Service)** $\rightarrow$ конфлікт переходів чи редагування закритої заявки викликає **`409 Conflict`**.

### 7.2. Специфікація HTTP-кодів відповідей

| Код | Призначення | Умови виникнення в системі | Вплив на базу даних |
| :--- | :--- | :--- | :--- |
| **`200 OK`** | Успішне читання або модифікація | • Успішне виконання `GET /health`, `GET /users`, `GET /issues`, `GET /issues/{id}`, `GET /issues/{id}/comments`.<br>• Успішне оновлення полів `PATCH /issues/{id}` відкритої заявки.<br>• Успішний або ідемпотентний перехід статусу в `PATCH /issues/{id}/status`. | Читання даних або фіксація валідних змін. При `no-op` запис не викликається. |
| **`201 Created`** | Успішне створення ресурсу | • Створення нової заявки `POST /issues`.<br>• Створення коментаря `POST /issues/{id}/comments`. | Вставка нового рядка в SQLite з автоінкрементним ID. |
| **`404 Not Found`** | Ресурс не знайдено | • Заявка з переданим `{id}` відсутня в БД при виклику `GET /issues/{id}`, `PATCH /issues/{id}`, `PATCH /issues/{id}/status`, `GET /issues/{id}/comments`, `POST /issues/{id}/comments`. | Жодних змін. |

### 7.3. Правила фільтрації та сортування
* **Фільтрація (`GET /issues`)**:
  * Параметри `status` та `priority` є опціональними. При передачі обох параметрів застосовується кон'юнкція (логічне **`AND`**).
  * Якщо за заданими фільтрами не знайдено жодного запису, сервер повертає статус `200 OK` та порожній масив `[]`. Повернення коду `404` для порожньої вибірки суворо заборонене.
* **Детерміноване сортування**:
  * Списки заявок та коментарів завжди повертаються в хронологічному порядку створення:  
    `ORDER BY created_at ASC, id ASC`.  
    Вторинне сортування за зростанням `id` гарантує абсолютну стабільність виведення записів, створених в одну й ту саму частку секунди.
