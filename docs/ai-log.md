## Запис 2. Формалізація правил PATCH та каталогу помилок (Крок 4)

* **Дата**: 01.11.2026
* **Учасник**: Siedashev Mykhailo
* **Інструмент / Модель**: Google Antigravity IDE (Режим: Agentic Mode) — Gemini 4 Argon
* **Мета**: Сформувати строгий технічний контракт поведінки `PATCH /issues/{id}` та чітко розмежувати HTTP статус-коди (404 vs 409 vs 422).
* **Переданий контекст**: Відфільтровані результати попереднього аналізу, правила нормалізації (trim), обмеження довжини рядків, довідник користувачів [1, 2].
* **Ключовий запит (Prompt)**:
  > «Використовуючи попередній аналіз, сформуй готові розділи специфікації: 1) Правила валідації та часткового оновлення (PATCH) з обов'язковою атомарністю та семантикою missing vs null; 2) Каталог помилок з чітким порядком перевірок та розмежуванням кодів 404, 409, 422, а також поведінку порожньої фільтрації (200 OK з [])».
* **Що запропонував AI**:
  * Чіткий ланцюжок перевірок: `schemas` (422) $\rightarrow$ `database` (404) $\rightarrow$ `service` (409).
  * Заборону передачі `null` для будь-яких полів, крім `assignee_id`.
  * Правило `extra = "forbid"` для Pydantic-моделі часткового оновлення.
  * Дворівневе забезпечення атомарності `PATCH`: відсікання змішаного невалідного пакету на рівні схеми Pydantic (`422` до звернення до БД) та транзакційний `rollback` сесії SQLite при збоях запису.
  * Повернення `200 OK` із порожнім масивом `[]` при відсутності збігів у фільтрах (замість 404).
* **Аналіз та рішення команди**:
  * Усі запропоновані положення визнано коректними, вони усувають неоднозначності без порушення бізнес-вимог замовника.
* **Спосіб перевірки**: Порівняння з вимогами REST API Guidelines та матрицею переходів статусів.
